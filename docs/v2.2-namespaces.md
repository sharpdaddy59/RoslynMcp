# v2.2 item D: `move_type_to_namespace` and `rename_namespace`

## Design note

Both tools live in `src/RoslynMcp/Tools/NamespaceTools.cs`, take `bool dryRun = false`
last, and return the usual write-tool shape (`applied, dryRun, wouldApply,
changedFileCount, changes, conflicts, staleFile, message`). Every write goes through
`MutationApplier.ApplyOrPreviewAsync`, so the compile gate and the stale-file check
apply to both. The only edit outside the new file: four helpers in
`FileOrganizationTools` (`ResolveTypeAsync`, `RemoveDeclaration`, `DetectNewline`,
`TrimLeadingBlankLines`) went from `private` to `internal` so they can be
reused.

**Where the decisions come from.** References come from `SymbolFinder.FindReferencesAsync`.
What a name binds to, whether it is an alias, and whether a namespace is already in
scope (an enclosing namespace, a using in the file or namespace block, or a project
`global using`) all come from the semantic model. Edits are `SyntaxEditor` node
replacements built with `SyntaxFactory`. Removing and appending whole declarations
splices text at syntax-node spans (the same `RemoveDeclaration` that
`move_type_to_file` uses). Nothing reads comments or string literals, so a comment or
literal that mentions the namespace is never changed. Tests prove it on a comment, a
literal, and prose in a doc summary.

### `move_type_to_namespace`

The type can be given by position or `fullyQualifiedName`. It refuses a nested type, a
type from metadata, and a type that is already in `newNamespace` (these return a
structured `applied: false` or a thrown error; see the table below). It also refuses
when `newNamespace` already contains a type with the same name and arity: this
pre-check names the clashing type and its file, and the gate is the backstop.

Each partial part is handled on its own, grouped by the namespace declaration that
encloses it:

| Part's enclosing namespace | Mechanics (`declarations[].mechanics`) |
|---|---|
| Top-level declaration holding only parts of this type | The namespace declaration's name is replaced (`renamedNamespaceDeclaration`). This covers both file-scoped and block namespaces. |
| Block namespace shared with other types (or the global namespace) | The part moves out together with its doc comments and attributes. It goes into a new `namespace New { ... }` block at the end of the same file, and the old block keeps the other types (`movedIntoNewBlockAtEndOfFile`). Usings declared inside the old block(s) are copied into the new block. |
| File-scoped namespace shared with other types | C# allows only one namespace in a file that uses a file-scoped namespace (CS8955), so a block cannot be added. The part moves to a new file next to the old one: `<TypeName>.cs`, or `<SourceFile>.<TypeName>.cs` if that name is taken (`movedIntoNewFile`, plus `newFile`). The new file gets the source file's non-global usings and `namespace New;`. |

Two alternatives were rejected for that last case. One was to convert the whole file to
block namespaces. That reindents every other type in the file and risks the contents of
raw or verbatim string literals. The other was to refuse. The new file is the same
approach `move_type_to_file` takes.

How references are fixed:
- **Qualified references** (`Old.Ns.Type`, `Old.Ns.Type.Member`, qualified crefs,
  `using static Old.Ns.Type`, alias targets `using T = Old.Ns.Type;`): the namespace
  qualifier is replaced with the new namespace. A leading `global::` is kept. A
  qualifier written relative to an enclosing namespace keeps its elided prefix when it
  still applies.
- **Simple-name references** outside the moved declarations: if `newNamespace` is not in
  scope at that point (no enclosing namespace, using or global using brings it in),
  `using New.Ns;` is added at compilation-unit level. This includes code that stays in
  the old namespace, such as `Price` in the fixture. If the existing plain usings are
  sorted, the new one goes in sorted position (System first); otherwise it goes after
  the last plain using.
- **What the moved type relied on from its old namespace.** These are names that
  resolved only because the declaration was inside `Old.Ns` or one of its parents, and
  that the new namespace's parents don't supply. Each type or extension method of that
  kind gets a `using` of its namespace. If a type with the same name in the new scope
  would capture the simple name instead, the name is fully qualified. A child namespace
  that was referenced by relative name (`Nested.Shelf` inside `Old`) is fully qualified,
  because a using directive never imports child namespaces.

### `rename_namespace`

Arguments are `oldNamespace`, `newNamespace` and `merge` (default false). The tool
refuses in these cases:
- `oldNamespace` has no namespace declarations in source, for example `System.Text`.
  The message says whether the namespace exists only in referenced assemblies.
- `newNamespace` already exists in source or in a referenced assembly and `merge` is
  false. The message names up to five declaring files and/or the assemblies.
- `merge: true` would put two types with the same name and arity into one namespace.
  Child namespaces are checked as well.

Child namespaces always move with the parent: `A.B` → `A.C` takes `A.B.D` → `A.C.D`,
including declarations, usings, `using static`, alias targets, qualified names and crefs.

**What Renamer could and could not do.** `Renamer.RenameSymbolAsync` on the
`INamespaceSymbol` (from the compilation of a project that declares it) works well when
only the last segment changes under the same parent. In the fixture, `FixtureLib.Catalog`
→ `FixtureLib.Inventory` covered:
- all four declarations, including the `Catalog` segment of
  `namespace FixtureLib.Catalog.Nested;`
- the using, the using static, the alias target and the cref
- the three qualified references across projects

and left comments and literals alone with the default options. Renaming into an
existing sibling (`merge: true` to `FixtureLib.LegacyShapes`) also worked. Renamer
cannot do the following, because its new name must be a single identifier:
- multi-segment targets (`FixtureLib.Catalog` → `FixtureLib.Inventory.Legacy`)
- moves to another parent (`A.B` → `C.B`)
- merges into an ancestor (`FixtureLib.Catalog` → `FixtureLib`)

So `rename_namespace` uses Renamer when the old and new names differ only in the last
segment (`mechanics: "renamer"`). In every other case it uses its own pass
(`mechanics: "syntax"`):
- Every namespace declaration whose full name is `Old` or `Old.*` is renamed. When the
  declaration sits inside an enclosing block, the name is computed relative to that
  block.
- Every name or member-access chain whose symbol is `Old` or a child of it is rewritten,
  except alias identifiers (their directive is rewritten instead).
- A relative name that does not spell out `Old`'s last segment is left alone, because
  its context is renamed with it.

Both paths are tested against the same fixture and produce the same edit sites. After
either path, a using that the rename made identical to another using in the same scope
is removed, so a merge cannot leave a CS0105 duplicate behind.

### Refusals: structured vs. thrown

| Case | Shape |
|---|---|
| Already in the target namespace; type-name collision; new namespace exists without `merge`; merge type collision; no source declarations | `applied: false`, `changedFileCount: 0`, `changes: []`, explanatory `message` (plus `dryRun: true, wouldApply: false` on a dry run) |
| Invalid namespace name, nested type, metadata type, symbol not found, a declaration nested in an outer block that the new name escapes | `{ "error": "..." }`, the same as the other tools' argument errors |

### Limits

- `rename_namespace` renames namespaces, not folders. Files stay where they are.
- A namespace declared inside an outer block (`namespace A { namespace B { } }`) can only
  be renamed to a name under that outer block. The syntax pass refuses otherwise, and
  you should flatten the block first.
- `move_type_to_namespace` does not rename or move files apart from the
  shared-file-scoped case above. When the old block keeps other types, the new block is
  appended to the same file.
- Linked files (one file in several projects) and `#if`-dependent namespace declarations
  are not handled specially. The compile gate catches anything that breaks.
- Silent rebinding: adding `using New.Ns;` to a file could make a simple name that used
  to bind elsewhere bind to a type from `New.Ns`. When that produces an ambiguity
  (CS0104), the gate rejects it. A rebinding that compiles is not detected, except for
  the moved type's own dependencies (see the capture check above).

## README subsections (ready to paste)

### `move_type_to_namespace`

Moves one top-level type to another namespace across the whole solution. Every
declaration moves, including all partial parts across files, and every reference keeps
resolving:
- Fully-qualified references, qualified crefs, `using static` and alias targets are
  re-qualified from `Old.Ns.Type` to `New.Ns.Type`.
- Files that use the type by simple name get `using New.Ns;` if the namespace is not
  already in scope. This includes code that stays behind in the old namespace.

How each declaration moves:
- **The namespace declaration holds only this type:** the declaration is renamed. This
  works for file-scoped and block namespaces.
- **Other types share a block namespace:** the type, with its doc comments and
  attributes, moves into a new `namespace New.Ns { }` block at the end of the same file.
- **Other types share a file-scoped namespace:** C# allows only one namespace in that
  file, so the type moves to a new `<TypeName>.cs` next to it.

Names the moved type relied on from its old namespace get a `using`. If a type with the
same name in the new namespace would capture the simple name, the name is fully
qualified instead.

The tool refuses nested types, metadata types, a move to the namespace the type is
already in, and a target namespace that already holds a type of the same name. Comments
and string literals are never touched. `declarations` reports the mechanics used for
each file. As with every write tool, the result is compiled first and nothing is written
if it wouldn't build.

### `rename_namespace`

Renames a namespace across the whole solution. This covers every declaration (block and
file-scoped, in every project) and every `using`, `using static`, alias target,
qualified name and cref. Child namespaces move with it, so `A.B` → `A.C` also renames
`A.B.D` → `A.C.D`.

Renames that change only the last segment under the same parent use Roslyn's
`Renamer`. Anything else, such as `A.B` → `A.X.Y` or a merge into a parent, uses a
symbol-driven syntax pass. The result reports which path was used as `mechanics`.

The tool refuses in these cases:
- The new namespace already exists, in source or in a referenced assembly. The message
  names where. Pass `merge: true` to combine the two namespaces deliberately.
- A merge would put two types with the same name into one namespace.
- The old namespace has no declarations in source (for example `System.Text`).

Comments and string literals are never touched, and usings that a merge makes identical
are collapsed. Files and folders are not renamed. The result is compiled before
anything is written.
