# v2.1: `move_type_to_file`

Draft section to fold into the README under "v2: tools that edit". It writes to disk, so
it goes through the same compile-before-write contract as `apply_rename` and
`extract_interface`.

### `move_type_to_file`

Moves one top-level type declaration out of a file that holds several types and into a
file of its own, in the same directory and the same project. The type's text is moved
as-is, including XML doc comments, attributes and any comments directly above it.
The new file gets:

- the source file's `extern alias` and `using` directives, copied exactly, including
  `static` and alias usings. **`global using` directives are not copied.** They already
  apply to every file in the project, and repeating a global alias in a second file is
  compile error CS1537, so the compile check would reject the move.
- the same namespace form as the source: file-scoped `namespace X;` or block
  `namespace X { }`. Nested block namespaces are rebuilt level by level, and each level
  keeps the usings declared inside it.
- the type declaration with its leading blank lines removed, so the file has exactly one
  blank line between the namespace (or usings) and the type.

The declaration is removed from the source file together with the blank line that
separated it from the previous member. Any blank lines that would double up at that
point are collapsed to one.

Tool description (as registered):

> Move one top-level type declaration out of a file that holds several types into its
> own file (default &lt;TypeName&gt;.cs, same directory, same project). The new file gets
> the source file's usings exactly as written (global usings excepted - they already
> apply project-wide), the same namespace form (file-scoped or block, including usings
> nested inside the block), and the type moved unchanged with its doc comments and
> attributes. Refuses nested types, partial types split across files, an existing
> destination file, and no-op moves. Compiles the result first via MutationApplier and
> writes nothing if it wouldn't build.

#### Parameters

| name | type | notes |
|---|---|---|
| `filePath` | string? | Absolute path of the file containing the type. Use with `line` + `column`. |
| `line` | int? | 1-based line number. It can point at the type's declaration or anywhere inside it, such as a member. The innermost type declaration that contains the position is the one chosen. |
| `column` | int? | 1-based column. |
| `fullyQualifiedName` | string? | Use this instead of a position, for example `FixtureLib.Square`, or ``Ns.Box`1`` for a generic type. The name of a member also works and selects the type that contains it. |
| `destinationFileName` | string? | Bare file name ending in `.cs`. Defaults to `<TypeName>.cs`, with no generic arity (`Box<T>` becomes `Box.cs`). A value containing a directory is rejected because the file is always created next to the source file. |

#### Result

```
{
  type: { name, kind, display, containingType },   // NavigationTools.Describe
  sourceFile: string,
  destinationFile: string,
  applied: bool,
  remainingTypesInSource: string[],   // top-level type names left in the source file
  changedFileCount: int,              // 2 when applied, 0 otherwise
  changes: [                          // empty when not applied
    { file, edits: [ { line, oldText, newText } ] },                     // the source file
    { file, added: true, edits: [ { line: 1, oldText: "", newText } ] }  // the new file
  ],
  conflicts?: [ { id, message, file, line, column } ],   // new compile errors, when rejected
  staleFile?: string,                                    // source changed on disk since load
  message?: string
}
```

A refusal returns `{ "error": "..." }` and writes nothing. That happens when:

- the type is nested inside another type;
- the type is `partial` with declarations in more than one file, or with more than one
  declaration in the same file;
- the destination file already exists on disk or in the loaded solution;
- the type is the only one in its file and the destination is that same file (a no-op);
- the type is the only one in its file and the destination is a different name, because
  the move would leave an empty file (rename the file instead);
- the source file is not part of the loaded solution, for example a source-generated
  file;
- `destinationFileName` is not a bare `*.cs` file name.

#### Example

`FixtureLib/Shapes.cs` contains `Circle`, `Square` and `ShapeKind` under `using System;`,
`using Text = System.String;` and `namespace FixtureLib;`.

```json
{ "tool": "move_type_to_file", "arguments": { "fullyQualifiedName": "FixtureLib.Square" } }
```

```json
{
  "type": { "name": "Square", "kind": "NamedType", "display": "FixtureLib.Square" },
  "sourceFile": "/repo/fixtures/FixtureSolution/FixtureLib/Shapes.cs",
  "destinationFile": "/repo/fixtures/FixtureSolution/FixtureLib/Square.cs",
  "applied": true,
  "remainingTypesInSource": ["Circle", "ShapeKind"],
  "changedFileCount": 2,
  "changes": [
    { "file": "/repo/fixtures/FixtureSolution/FixtureLib/Shapes.cs", "edits": [ { "line": 22, "oldText": "...", "newText": "" } ] },
    { "file": "/repo/fixtures/FixtureSolution/FixtureLib/Square.cs", "added": true, "edits": [ { "line": 1, "oldText": "", "newText": "..." } ] }
  ]
}
```

`Square.cs` now contains:

```csharp
using System;
using Text = System.String;

namespace FixtureLib;

/// <summary>A square with a given side length.</summary>
[Serializable]
public readonly record struct Square(double Side)
{
    public double Area => Math.Pow(Side, 2);

    public Text Label() => $"{ShapeKind.Angular} {Side}";
}
```

`Shapes.cs` keeps `Circle` and `ShapeKind`, separated by a single blank line.
`FixtureLib.csproj` is byte-identical to before. `Workspace.TryApplyChanges` adds a
`<Compile Include="Square.cs" />` item, but MutationApplier strips it because the SDK
glob already includes the file, and it restores the csproj's original final newline. The
live workspace already contains the new document, so `symbol_search` and
`go_to_definition` resolve `Square` to `Square.cs` without a reload.

#### Known limitations

- **Every using is copied, needed or not.** The tool does not prune usings the moved type
  doesn't use, and it does not remove usings from the source file that only the moved
  type needed. Both cases are at most IDE0005/CS8019 hints, never errors.
- **Leading comments go with the type.** Any comment directly above the declaration
  moves with it, including a section comment that was really about the file. If the type
  is the first one in a file with no usings and no namespace, a file-header or license
  comment can move with it too.
- **Preprocessor directives are not rebalanced.** A `#pragma warning disable` or
  `#region` directly above the type moves with it, and the matching
  `restore`/`#endregion` stays behind (it is leading trivia of the next member). Pragmas
  still compile. An `#if`/`#endif` or `#region` pair split this way is reported as a new
  compile error and the move is rejected. Conditional-compilation blocks that wrap
  several types are not handled.
- **Partial types are refused** rather than moved part by part.
- **The source must keep at least one type.** Moving the last type out of a file to a new
  name (a file rename) is refused. Use your file tools to rename the file.
- **The destination is always next to the source.** There is no cross-folder or
  cross-project move. The new document inherits the source document's `Folders`.
- **The text is not reformatted.** The new file uses the source file's line endings and
  encoding, and the type keeps its original indentation. If the namespace form is the
  same, as it always is here, that indentation is correct.
