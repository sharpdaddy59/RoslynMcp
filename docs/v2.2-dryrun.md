# v2.2 item A: `dryRun` on every write tool

## Design note

Every write tool (`apply_rename`, `extract_interface`, `change_signature`,
`delete_member`, `move_type_to_file`) now takes `bool dryRun = false` as its last
parameter.

**One validation stage, two endings.** `MutationApplier.TryApplyAsync` was split into a
private, side-effect-free `ValidateAsync` (staleness check on every touched document,
compile gate of every affected project against the load-time baseline errors, and the
list of files that would change) and the apply stage (csproj snapshot,
`Workspace.TryApplyChanges`, snapshot refresh, redundant `<Compile Include>` cleanup).
`TryApplyAsync` runs both stages and behaves exactly as before. The new
`MutationApplier.PreviewAsync(candidate)` runs only the validation stage, so it never
calls `WorkspaceHost.TryApplyChanges`, never writes a file (csproj included), and leaves
`WorkspaceHost.Current` untouched. `MutationApplier.ApplyOrPreviewAsync(candidate, dryRun)`
picks one of the two, which is the single call each tool makes.

**Result shape.** `MutationResult` gained two optional trailing positional members,
`bool DryRun = false` and `bool WouldApply = false`, plus a computed `Accepted`
(`Applied || WouldApply`). Existing factory methods and `new(...)` call sites are
unchanged. A preview that passes returns `Applied=false, DryRun=true, WouldApply=true`,
with `ChangedFiles` set to the files that would change and the message
`"Dry run: the edit would be applied; N file(s) would change. Nothing was written."`.
A preview that fails returns the real rejection (`NewErrors`, `StaleFile`, `Message`
identical to what `TryApplyAsync` would return) with `DryRun=true, WouldApply=false`.

**Tool JSON.** Each tool computes its candidate exactly as before and returns the same
JSON shape, plus `dryRun: true` and `wouldApply: true|false` when `dryRun` is set
(both fields are omitted on real calls, so non-dry-run output is unchanged). `changes`
and `changedFileCount` are filled whenever the edit was applied or would be applied;
`conflicts` / `staleFile` / `message` come straight from the shared rejection. The tools'
own pre-checks (delete_member's reference/contract refusal, change_signature's
unsupported-usage refusal, all thrown argument errors) run identically in dry-run mode;
the two structured refusals also report `dryRun: true, wouldApply: false`.

**One additive change to a real call.** `extract_interface` previously returned no
`changes` list. To let a dry run show "the same changes the real call reports", it now
returns `changedFileCount` and `changes` (the class file's base-list edit, if any, plus an
`added: true` entry carrying the generated interface text, the same convention
`move_type_to_file` uses) on both real and dry-run calls.

**`rename_symbol_preview`** keeps its behaviour for back-compat; its description now
points at `apply_rename` with `dryRun: true`, which shows the same edits plus the
compile-gate verdict.

**Tests.** `tests/RoslynMcp.Tests/DryRunTests.cs`: for each tool, a dry run's `changes`
is JSON-identical to the following real call's, every file under
`fixtures/FixtureSolution` (bin/obj excluded) hashes identically across the dry run, and
a rejected dry run reports the same `conflicts` (or `staleFile`) and `message` as the real
call. Rejected cases: apply_rename to `Handle` (CS0111), extract_interface from `Shipper`
(duplicate `IShipper`, CS0101), change_signature removing the still-read `weightKg`
(CS0103), delete_member `force: true` on `LiveHelper` (CS0103), move_type_to_file with a
source file touched on disk after load (stale). Plus `PreviewAsync` unit tests (passes:
`WouldApply`, workspace reference and disk unchanged; fails: same `NewErrors` and
`Message` as `TryApplyAsync`).

## README subsection (ready to paste)

### dryRun on every write tool

Every write tool (`apply_rename`, `extract_interface`, `change_signature`,
`delete_member`, `move_type_to_file`) accepts `dryRun: true`. A dry run computes the edit
exactly as the real call would, runs every check (the tool's own refusals, the
stale-file check, and the compile-before-write gate), and reports the result, but writes
nothing: no source file, no new file, no project file, and the loaded workspace is left as
it was. The response has the tool's usual shape plus `dryRun: true` and `wouldApply`:
when `wouldApply` is true, `changes` is the exact edit list the real call will write; when
it is false, `conflicts` (or `staleFile`) holds the same compiler errors the real call
would reject with. Re-run the same call without `dryRun` to apply. `rename_symbol_preview`
still works, but `apply_rename` with `dryRun: true` is preferred because it also gives the
compile-gate verdict.

```json
{
  "symbol": { "name": "Process", "kind": "Method", "display": "FixtureLib.ProcessorBase.Process(string)", "containingType": "FixtureLib.ProcessorBase" },
  "newName": "Execute",
  "applied": false,
  "dryRun": true,
  "wouldApply": true,
  "changedFileCount": 2,
  "changes": [
    { "file": "/repo/FixtureLib/Processor.cs", "edits": [ { "line": 13, "oldText": "Process", "newText": "Execute" }, { "line": 21, "oldText": "Process", "newText": "Execute" } ] },
    { "file": "/repo/FixtureApp/Program.cs", "edits": [ { "line": 7, "oldText": "Process", "newText": "Execute" } ] }
  ],
  "message": "Dry run: the edit would be applied; 2 file(s) would change. Nothing was written."
}
```
