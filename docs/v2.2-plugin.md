# v2.2 item G: Claude Code plugin

## (a) Design note

### Where the format came from

On 2026-10-13 a claude-code-guide agent read the current Claude Code docs: the plugin manifest reference, the marketplace reference, create-marketplace, the CLI reference, the MCP page, and the hooks page under code.claude.com/docs/en/plugins/. Separately, `claude plugin --help` on aransas lists a `validate [--strict] [--json] <path>` command, and I used it on both manifests. The format points that matter here:

- **Plugin manifest.** The manifest lives at `<plugin>/.claude-plugin/plugin.json`, and only `name` is required (kebab-case). `version`, `description`, `author` (`{name, email?, url?}`), `homepage` (which must parse as a URL), `repository`, `license`, and `keywords` are optional. Leaving out any of the first three produces a warning.
- **MCP server.** A plugin can declare its MCP server in `<plugin>/.mcp.json` (wrapped in `{"mcpServers": {...}}`, loaded automatically) or inline under `mcpServers` in plugin.json. `${CLAUDE_PLUGIN_ROOT}` expands in stdio `command`, `args`, and `env`. Neither form has a per-platform command key.
- **Marketplace.** The marketplace manifest lives at `<repo>/.claude-plugin/marketplace.json` and needs `name`, `owner{name}`, and `plugins[]`. Each plugin entry needs `name` and `source`. A relative `source` must start with `./` and resolves from the repo root. The marketplace entry name has to match the plugin.json `name`. Marketplace names may use letters, digits, `.`, `_`, and `-`. Some names are reserved (such as `claude-plugins-official`, `github`, and `npm`), but `roslynmcp` is not.

### Decisions

- **Layout.** The plugin is `plugin/` (named `roslyn`), and the marketplace manifest at the repo root (`.claude-plugin/marketplace.json`, named `roslynmcp`) points at it with `source: "./plugin"`. That gives `/plugin marketplace add sharpdaddy59/RoslynMcp` followed by `/plugin install roslyn@roslynmcp`.
- **Server declaration.** The server goes in `plugin/.mcp.json` rather than inline: `"roslyn": {"command": "bash", "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/roslyn-mcp.sh"]}`. Using `bash` as the command means the script does not depend on its exec bit surviving the marketplace clone. The repo `.gitignore` ignores `.mcp.json` for SharpCoder's working files, so I added a negation, `!plugin/.mcp.json`.
- **Bootstrap location.** The bootstrap runs in the MCP command, not in a SessionStart hook. A hook would run on every session and add text to Claude's context. A command hook also cannot hand anything to the server, and the server would still need its own "is it installed?" check. With the check in the launcher, the cost after the first launch is one `command -v` before `exec`, and nothing else happens on later sessions. The guide flagged a possible risk: a slow first download could exceed the MCP startup window (`MCP_TIMEOUT`, whose default the guide did not find). Measured locally, a fresh install from a local folder takes under 2 seconds. Downloading the roughly 10.4 MB nupkg from GitHub adds network time. If a slow link causes a timeout, the install still completes, and the next launch (`/mcp` reconnect, or a restart) finds the tool. The workaround is `MCP_TIMEOUT=60000 claude` for that first run.
- **Pinned version and private feed.** The id `RoslynMcp` on nuget.org belongs to an unrelated project, which is at 1.2.3 as of today. The plain `--add-source` install in the README still queries nuget.org, and it would pick the other project if that project ever published a version higher than ours. The script avoids this in two ways. It pins `--version` to the version in the downloaded file name. It also installs with `--configfile` pointing at a temporary nuget.config that `<clear/>`s every feed except the download folder. The same fix would be worth making in the README's manual instructions.
- **Existing installs.** If `dotnet tool install` fails because a copy is already registered (shadowed or broken), the script falls back to `dotnet tool update` with the same arguments.
- **Shim lookup.** The script checks `~/.dotnet/tools/roslyn-mcp` and `roslyn-mcp.exe` as well as `PATH`. The `.exe` form is for Git Bash on Windows.
- **Windows.** No per-platform command exists, so `scripts/roslyn-mcp.ps1` ships as a manual alternative, documented in `plugin/README.md`. You run it once to install, and after that the bash launcher finds `roslyn-mcp.exe`. The other option is the plain `.mcp.json` route.
- **Versions.** plugin.json and the marketplace entry both say `version: "2.2.0"`, matching the upcoming package. The csproj is still at 2.1.0, and I did not change it. Setting a plugin version pins it: users get plugin updates only when this string changes, so bump it with each release. `claude plugin tag` checks that plugin.json and the marketplace entry agree. The plugin version has no effect on which tool version gets installed, because the bootstrap always takes the latest release.

### What could not be verified (no release tagged yet)

- **The live GitHub download path.** I did run it: `releases/latest` currently returns 404, and the script exits 1 with a clear stderr message and nothing on stdout. A real asset download has not been exercised, so the asset-URL grep needs one check against the first real release. The `gh` fallback and the PowerShell script were not run at all (this machine has no pwsh).
- **Installing through Claude Code.** I did not run `/plugin marketplace add` or `/plugin install`, because the task said not to touch the user's Claude Code. `claude plugin validate` passes on both manifests, but nobody has yet watched Claude Code actually spawn the server from the plugin.
- **`MCP_TIMEOUT` with a first-run download** over a slow network.
- **Windows.** Untested.

## (b) Smoke test

Setup: I packed the nupkg with `dotnet pack src/RoslynMcp -c Release -o <scratchpad>/plugin-pack`, which produced `RoslynMcp.2.1.0.nupkg` (10.4 MB). The driver piped the following into `bash plugin/scripts/roslyn-mcp.sh` and captured stdout and stderr separately:

1. The `initialize` request (`protocolVersion 2025-06-18`)
2. A 2-second pause
3. `notifications/initialized`
4. Another 2-second pause, then EOF

Each run used a temporary `HOME` and `DOTNET_CLI_HOME`, so the real `~/.dotnet/tools` was not touched. Except for run 3, `PATH=/usr/bin:/bin`.

| Run | Branch | Env | Exit | stdout | stderr |
|-----|--------|-----|------|--------|--------|
| 1 | Install from local folder | fresh HOME, `ROSLYN_MCP_NUPKG_DIR=<pack dir>` | 0 | exactly 1 line, the initialize response | bootstrap lines, the dotnet first-run banner, `Tool 'roslynmcp' (version '2.1.0') was successfully installed.`, server logs |
| 6 | Same, timed | second fresh HOME | 0 | the same single line | the same; wall time 4.0 s, which equals the 4 s of stdin pacing, so the install overlapped |
| 2 / 7 | Already installed in `~/.dotnet/tools`, not on PATH | HOME from run 1, no override | 0 | the same single line | server logs only, no bootstrap lines |
| 3 | Already on PATH | empty HOME, `PATH=<home1>/.dotnet/tools:/usr/bin:/bin` | 0 | the same single line | server logs only |
| 4 | dotnet missing | `env -i HOME=<empty> PATH=/nonexistent` | 1 | 0 bytes | "roslyn-mcp is not installed and the 'dotnet' CLI was not found." plus the SDK install hint |
| 5 | GitHub path, no release yet | empty HOME, no override | 1 | 0 bytes | "downloading the latest release…", `curl: (22) … 404`, "no RoslynMcp .nupkg found on the latest release" |

The stdout of every successful run, byte for byte:

```
{"result":{"protocolVersion":"2025-06-18","capabilities":{"logging":{},"tools":{"listChanged":true}},"serverInfo":{"name":"RoslynMcp","version":"2.1.0"}},"id":1,"jsonrpc":"2.0"}
```

All install output went to stderr, including the "Welcome to .NET" banner from first use of a fresh DOTNET_CLI_HOME and the "tools directory is not on PATH" advice. stdout held nothing but JSON-RPC.

## (c) README section (paste ABOVE `## Install`)

````markdown
## Install as a Claude Code plugin

The quickest way to use RoslynMcp from Claude Code is to run these two commands inside Claude Code:

```
/plugin marketplace add sharpdaddy59/RoslynMcp
/plugin install roslyn@roslynmcp
```

On Claude Code 2.1.275 or later, one command does both steps: `/plugin install roslyn --marketplace sharpdaddy59/RoslynMcp`.

The plugin registers an MCP server named `roslyn`. The first time it starts, its launcher looks for `roslyn-mcp`, checking `PATH` and then `~/.dotnet/tools`. If the tool is missing, the launcher downloads the `.nupkg` from the latest GitHub Release, installs it with `dotnet tool install -g`, and starts it. After that it simply runs the installed tool. The .NET 10 SDK must already be installed. Install progress goes to stderr, which shows in `claude --debug` or the `/mcp` panel. If a slow download makes the first start time out, run `/mcp` to reconnect, because the install will have finished, or start Claude Code once with `MCP_TIMEOUT=60000`.

- **Offline or pinned installs:** set `ROSLYN_MCP_NUPKG_DIR` to a folder that holds `RoslynMcp.*.nupkg`, and the launcher installs from that folder instead of GitHub.
- **Updating:** the plugin never upgrades an installed tool. To upgrade, use `dotnet tool update` as described under Install below.
- **Windows:** the launcher is a bash script. It should work when Git for Windows' `bash` is the one on `PATH`. If it is not, run `plugin/scripts/roslyn-mcp.ps1` once in PowerShell to install the tool, or use the manual `.mcp.json` setup below.
````
